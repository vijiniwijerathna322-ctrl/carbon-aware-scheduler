# 09 Monitoring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Detect when the deployed model degrades: input drift (PSI, KS), error drift (MAE vs backtest), and — most importantly for this project — **loss of interval calibration** (realized coverage vs the 80% promise).

**Architecture:** Pure statistical functions; a `build_monitor_report` that *replays* the current model over the most recent days using only data available at each issue time (no forecast log needed); JSON + HTML outputs; CLI command; a status endpoint in the API.

**Tech Stack:** numpy, scipy (`ks_2samp`, `binomtest`), pandas; Evidently optional for an HTML extra.

**Spec:** `specs/2026-10-11-carbon-aware-scheduler-design.md` (decision D9)

## Global Constraints

- Reference window: 180 days ending at the model's `fit_end`; current window: last 14 days of data
- PSI with 10 quantile bins from the reference; thresholds `warn ≥ 0.1`, `alert ≥ 0.25`
- KS test p-value threshold 0.01 (two-sample, per feature)
- Coverage alert: two-sided exact binomial test of realized coverage vs nominal 0.8 at p < 0.01 over the current window, with at least 100 forecast points
- MAE ratio alert: recent MAE / backtest MAE ≥ 1.5 → `warn`, ≥ 2.0 → `alert`
- Monitored features: `y_issue`, `roll_mean_24`, `roll_std_24` and the targets
- Gate per task: ruff, format check, mypy, pytest; Conventional Commits

## Review Focus

- Constant or near-constant reference feature (zero-width bins) → PSI must return a defined value or raise a clear error, never `inf`/NaN silently
- Fewer than 100 realized points → status `insufficient_data`, not a false `ok`
- Current window containing the data gap (NaN) → excluded and counted, not treated as zero
- Replay must use only data ≤ each issue time (reuse backtest truncation) — test with a spy
- Status endpoint with no report yet → 404-style explicit message, not 500
- A single outlier hour must not trip the coverage alert (needs ≥ 100 points)

## Execution amendments and evidence

The executing-plans sub-skill was unavailable; this plan was followed directly. Statistics tests are grouped in `test_statistics.py`; CLI and endpoint tests are grouped in `test_report.py`. Coverage values and p-values may be null when unavailable. MonitorReport additionally includes replay counts, baseline diagnostics, provenance and limitations.

Replay excludes issues before artifact fit_end and keeps the latest eligible prediction per realized target hour. Current windows can overlap the reference; overlap is reported. MAE baselines require earlier raw held-out predictions with matching model configuration, excluding weather experiments. Approved weather pointers require vintage forecast logs. Diagnostic p-values do not correct serial dependence, seasonality or multiple tests. See ADR 0017.

Verified locally: 295 tests, 92.95% coverage, ruff and mypy; real CLI exit 2; strict JSON and self-contained HTML; isolated real-data simulation coverage 82.14% before shift and 67.09% at day 7. Overall input alarms existed before the shift. Sampled coverage detection delay is greater than 3 and at most 7 days. No production artifact or raw-data mutation. Linux/Docker CI is recorded in the master plan after publication.

Published implementation CI: [38335120969](https://github.com/vijiniwijerathna322-ctrl/carbon-aware-scheduler/actions/runs/38335120969), Linux checks and Docker smoke both successful. Tasks were delivered together in one implementation commit because the shared statistics/report tests cross task boundaries, followed by this completion record.
